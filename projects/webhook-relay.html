What

Webhook Relay accepts events, creates a delivery job for every HTTP endpoint subscribed to that event type, and delivers them asynchronously through a database-backed worker. Failed deliveries are retried with capped exponential backoff and full jitter. Deliveries that run out of attempts, or fail for a non-retryable reason, move to DEAD and can be replayed by hand. Requests are signed with HMAC-SHA256, each endpoint has its own token-bucket rate limit, and delivery outcomes and latencies are exported to Prometheus.

Why I designed it this way

  • PostgreSQL as both store and queue. Writing the event and its delivery jobs in one transaction means an accepted event can never be missing its jobs, and there's no separate broker to run. The cost is polling overhead and extra database load.
  • Safe concurrent workers. Workers claim jobs with SELECT … FOR UPDATE SKIP LOCKED, so two workers never take the same row. Each claim has a lease: if a worker dies, the lease expires and another worker reclaims the job. Fencing checks reject results from a worker that no longer owns the job.
  • At-least-once, stated honestly. A receiver can process a webhook before the worker records success. If the worker crashes in that window, the delivery is retried, so receivers should be idempotent.
  • Flyway owns the schema. Applied migrations are never edited, and Hibernate runs with ddl-auto=validate, so the schema history stays reproducible.
  • The database enforces the rules. CHECK constraints restrict statuses, one delivery per (event, endpoint), and a lease timestamp only while IN_PROGRESS. Partial indexes keep finished history out of the active-job indexes.
  • Sign the bytes that are sent. jsonb doesn't keep the original bytes, so the sender signs the exact body it transmits. The signature includes a timestamp checked against a ±5-minute window with a constant-time comparison.

Results I verified

2,564 / 2,564deliveries succeeded across 4 local k6 runs
16.0 s → 0.53 sp95 end-to-end latency, 1 worker → 2 workers (−96.7%)
10 / 10events delivered after a receiver outage, none missing
130 / 130automated tests passing
  • The latency benchmark ran at 20 events per second for 60 seconds (1,201 events) against the same PostgreSQL queue. The two workers split the load 623 / 578.
  • For crash recovery, I killed a JVM worker with SIGKILL mid-delivery. A second worker reclaimed it only after the lease expired, and the attempt history stayed consistent. The receiver saw the duplicate request, which is the expected at-least-once behaviour.

These are controlled local experiments with a mock receiver. They don't establish production throughput, availability or exactly-once delivery.

What's next

A server-rendered delivery history UI (Thymeleaf) is in development. Grafana dashboards, alerting rules and a public HTTPS deployment are planned.

What I learned

  • "Reliable" needs a precise definition. At-least-once delivery means duplicates can happen. I learned to state the guarantee plainly and make receivers idempotent, instead of implying exactly-once.
  • Concurrency can be handled in the database. Row locking with SKIP LOCKED, leases and fencing checks, backed by CHECK constraints, kept multiple workers correct without a separate coordination service.
  • Measure before guessing where the bottleneck is. In the k6 runs, API p95 stayed around 17 ms while end-to-end latency was 16 s. That pointed at delivery throughput, not the API, and adding one worker cut end-to-end p95 by 96.7% with no code change.
  • Fault injection shows what tests alone don't. Killing a real worker with SIGKILL confirmed lease recovery end to end, and let me see the duplicate delivery my design predicted.
